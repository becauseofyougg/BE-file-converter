01 · Два несущих решения

HTTP-запрос никогда
не выполняет конвертацию

запись задачи→ presigned URL→ клиент льёт в S3→ 202→ очередь→ воркер

И второе, не менее важное: задачами владеет gateway, у воркеров нет своей БД. Поэтому конвертеров может быть два, три или пять — модель данных от этого не меняется.

02 · Разбиение

Пять сервисов

api-gateway

Единственная точка REST. JWT локально, presigned-ссылки, владеет задачами: создаёт, слушает результаты, пишет статус.

БД gateway

identity-service

Регистрация, вход, JWT и refresh, подтверждение email, сброс пароля.

БД identity

image-service

Изображения на sharp. Лёгкий образ без внешних бинарников.

без БД · CPU · ×N

data-service

csv, json, xml, yaml — все 12 направлений. Чистый Node.

без БД · CPU · ×N

notification-service

SSE-соединения браузеров, история уведомлений, auth-письма.

БД notification

Второй конвертер в обсуждении назывался «текстовым». Здесь он data-service: он про структурированные текстовые форматы, а не про документы. docx → pdf станет третьим сервисом со своим образом.

02 · Обоснование

Почему граница проходит здесь

  • 01Между конвертерами — по весу образа, а не по домену. У image-service только sharp. Любой тяжёлый движок, который появится позже, добавит сотни мегабайт — и добавит их своему сервису, не задев остальные.
  • 02Аутентификация вынесена, чтобы gateway не был связан с таблицей пользователей.
  • 03Нотификации вынесены, потому что живое SSE-соединение — это память и счётчик коннектов, а не CPU.
  • —Задача не может иметь двух владельцев. Список задач должен быть одним запросом с пагинацией, а не склейкой из двух источников — поэтому conversion_jobs в БД gateway, а воркеры в базу не ходят вообще.

Потоки запросов, сообщений и байтов

03 · Репозиторий

Общее ядро воркера обязательно

apps/
  api-gateway/            // REST + владелец задач
  identity-service/       // RMQ request/response
  image-service/          // RMQ-консьюмер, sharp
  data-service/           // RMQ-консьюмер, csv/json/xml/yaml
  notification-service/   // SSE + история + SMTP
libs/
  core/ contracts/ storage/ observability/
  worker-kit/             // скачать → проверить → конвертировать → залить

Оба конвертера делают одно и то же и различаются только реестром конвертеров. Без worker-kit получатся два почти одинаковых сервиса — и это первое, за что зацепится ревьюер.

04 · Обмен сообщениями

Три exchange с разными ролями

conversion.commands

convert.image и convert.data — две очереди, два деплоймента, два образа.

conversion.results

Воркер отчитывается result.completed. Слушает только gateway.

domain.events

Публичные события. У notification-service две очереди: общая под письма и эксклюзивная на реплику под SSE.

Почему результат идёт через gateway. Публичное conversion.completed выпускается только после коммита состояния. Иначе пользователь получит SSE «готово», дёрнет ссылку и поймает 409 NOT_READY, потому что статус ещё не применён.

04 · Надёжность

Гарантии доставки

  • 01Одна задача за раз на воркер. prefetchCount: 1, ручной ack. Падение переотправляет ровно одну задачу.
  • 02Идемпотентность живёт в gateway. Воркер без БД не может проверить статус — зато повторный result.completed по завершённой задаче это no-op.
  • 03Transactional outbox в gateway и identity: строка состояния и строка outbox — одной транзакцией.
попытка 1→ +10 с→ +60 с→ +300 с→ DLQ · FAILED

Permanent-ошибки — битый вход, неподдерживаемая пара, NOT_TABULAR — не тратят три попытки впустую.

05 · Пайплайн

Статус пишет только gateway

PENDING→ QUEUED→ PROCESSING→ COMPLETED→ EXPIRED
↳ RETRYING↩ · FAILED · CANCELLED

Каждый переход пишет строку в job_events — журнал отвечает на вопрос «почему задача шла четыре минуты» без раскопок в логах.

Воркер за всю обработку не делает ни одного запроса в БД. В команде уже есть всё: sourceKey, resultKey, форматы, опции. Тип файла он перепроверяет по сигнатуре, а не по расширению.

06 · Данные

12 направлений из 8 кусков кода

csvjsonxmlyaml → parse → каноническая модель → serialize → csvjsonxmlyaml

Csv, json, xml и yaml — это разные представления одной структуры. Поэтому не 12 конвертеров, а 4 парсера и 4 сериализатора.

Пятый формат добавит сразу 8 новых направлений ценой двух кусков вместо восьми. И тестируется отдельно: парсер — на «прочитал правильно», сериализатор — на «записал правильно», без комбинаторного взрыва пар. Матрица в GET /formats считается, а не пишется руками.

06 · Подводный камень

Не всякое дерево ложится в таблицу

// Ложится в CSV: массив плоских объектов
[{ "id": 1, "name": "Анна" }, { "id": 2, "name": "Борис" }]

// Не ложится: вложенность и разнородные ключи
{ "user": { "name": "Анна", "tags": ["a", "b"] } }

flatten: false — по умолчанию

Документ отклоняется с NOT_TABULAR. Permanent-ошибка: пользователь получает внятную причину, а не битый CSV.

flatten: true

Вложенность разворачивается в ключи через точку: user.name, user.tags.0.

У xml свои конвенции — rootName, itemName, attributePrefix, textKey. Без них xml → json → xml не даст исходный документ, и это первое, что проверит round-trip тест.

07 · Хранилище

Байты не проходят через Node вообще

  • 01Загрузка — presigned PUT в три шага: POST /conversions отдаёт ссылку, клиент льёт прямо в MinIO, POST /:id/uploaded проверяет объект через headObject и ставит в очередь.
  • 02Подпись фиксирует ключ, тип и лимит размера. У yaml и xml он ниже — они разбираются целиком в память.
  • 03Скачивание — 302 на presigned GET после проверки job.user_id. Ключ результата вычисляет gateway: воркер не может записать не туда.
  • 04Исходник удаляется после успешной конвертации, результат — по expires_at.

11 · Безопасность

Разбор данных — это тоже атака

Парсеры

xml — отключённые внешние сущности (XXE) и лимит глубины. yaml — безопасный загрузчик без произвольных тегов. json — лимит вложенности. Именно на этих трёх местах ломают конвертеры форматов.

Изоляция воркеров

Non-root, read-only ФС кроме временного каталога, сброшенные capabilities, без сети наружу, лимиты CPU и памяти, таймаут на задачу.

Учётные данные

argon2id, access JWT 15 мин, ротируемый refresh в httpOnly-cookie. Подпись проверяется локально в gateway.

Приём файлов

Allow-list расширений, проверка по сигнатуре, лимит размера в самой подписи. Имя файла никогда не становится ключом — ключ это UUID задачи.

15 · Что нужно решить

Открытые вопросы

  1. Какие направления у изображений? Данные зафиксированы, картинки — нет. Предлагаю png, jpeg, webp, avif, tiff во всех направлениях плюс ресайз: на sharp это столько же работы, сколько одно направление.
  2. Максимальный размер файла и срок хранения — 100 МБ и 24 ч пока заглушки; для yaml и xml лимит должен быть ниже.
  3. flatten по умолчанию: отклонять невыровненный документ или разворачивать через точку?
  4. Обязательно ли подтверждение email до первой конвертации?
  5. Входит ли в скоуп админский раздел — все задачи, переотправка, статистика?
  6. Целевая нагрузка: от неё зависит, нужны ли quorum-очереди и outbox.
