01Summary

The service accepts a file, converts it to another format asynchronously, and delivers the result. The gateway creates a job and issues a presigned URL, the client uploads the file straight to storage, a command goes onto a queue, and the worker for that format family picks it up.

Two decisions carry the whole structure:

  1. HTTP requests never convert. That lets a heavy file and a slow engine coexist without holding a connection open, and it is what gives the microservice split a real reason to exist rather than a decorative one.
  2. The gateway owns the jobs; workers have no database. A worker is a pure compute step: take a command, download, convert, upload, report an event. That is why there can be two converters, or three, or five, without the data model changing.

02Service decomposition

ServiceResponsibilityOwnsScales with
api-gateway The only REST surface. Verifies JWTs locally, issues presigned URLs, and owns the conversion jobs: creates them, consumes worker results, writes status. Rate limiting, quotas, OpenAPI. gateway HTTP concurrency
identity-service Registration, login, JWT issue and refresh, email verification, password reset, profile. identity low
image-service Image conversion on sharp. Stateless, N replicas, a light image with no external binaries. — CPU
data-service Structured-data conversion: csv, json, xml, yaml — all 12 directions. Stateless, N replicas, pure Node. — CPU
notification-service Notification delivery: holds the browsers' SSE connections and pushes job status, keeps the history, sends auth mail over SMTP. notification live connections

On the name. In discussion the second converter was called "the text service". Here it is data-service, because it handles structured text formats rather than documents: if docx → pdf appears later, that is a third service with its own image and its own queue, not an extension of this one.

Why the boundary falls here

  • Between the converters, the split is by image weight, not by domain. image-service carries only sharp, so its image stays light. Any heavyweight engine added later (LibreOffice, ffmpeg) brings hundreds of megabytes — and brings them to its own service, leaving the others untouched. A forty-minute video must not block a 200 ms thumbnail resize, and separate queues on separate deployments are the only way to guarantee that.
  • Auth is split out to keep the gateway free of user-table coupling and to give a clean example of a synchronous call over the broker.
  • Notifications are split out because a live SSE connection costs memory and a connection slot, not CPU. A thousand waiting tabs and a thousand REST requests per second load a process in completely different ways, and the two must scale independently.
The key consequence

With more than one converter, a job cannot have two owners: the user's job list must be one paginated query, not a merge across sources. So conversion_jobs lives in the gateway's database and the workers never touch a database at all. Adding a third converter requires no migration.

03Repository layout

Nest monorepo mode, in the current repository. The existing src/core/* modules move to libs/core and are imported by every app unchanged.

apps/
  api-gateway/            // REST + owner of the jobs
  identity-service/       // RMQ handlers, request/response
  image-service/          // RMQ consumer, sharp
  data-service/           // RMQ consumer, csv/json/xml/yaml
  notification-service/   // SSE + history + SMTP
libs/
  core/                   // config, database, health, throttler (moved from src/core)
  contracts/              // messages, payloads, schemas, error codes, format matrix
  worker-kit/             // SHARED worker core: download → verify → convert → upload
  storage/                // S3 client: put, get stream, presign, delete
  observability/          // pino logger, correlation-id, metrics
Why worker-kit is mandatory

Both converters do the same thing: download from S3, verify the signature, convert, upload the result, report an event, clean up the temp directory. Only the converter registry differs. Without a shared library you end up with two nearly identical services — the first thing a reviewer will pick on. With it, image-service and data-service are thin shells: their own providers and a queue name.

Migration steps from the current boilerplate

  1. nest-cli.json → monorepo mode, projects entries for five apps and five libs.
  2. git mv src/core libs/core; the src/modules/* stubs move into their owning apps.
  3. tsconfig.json paths: @core/*, @contracts/*, @worker-kit/*, @storage/*.
  4. Split main.ts: the gateway keeps today's Fastify bootstrap (compression, cookies, CORS, validation pipe, transactional context); workers use NestFactory.createMicroservice with Transport.RMQ plus a minimal HTTP listener for /health.
  5. The Config interface is extended per app: a worker needs neither SMTP credentials nor a database URL — only RabbitMQ and S3.
  6. Only three apps have migrations at all: gateway, identity, notification.

04Messaging design

Transport is @nestjs/microservices over RabbitMQ. Three exchanges, with distinct roles.

Why the result goes through the gateway rather than straight to the user

A worker publishes result.completed, which is an internal fact: "the file is converted, the result is at this key." The gateway applies it to its table and only after the commit publishes the public conversion.completed onto domain.events, where notification-service picks it up and pushes it to the browser.

The extra hop pays for itself. If SSE were pushed directly from the worker's event, the user would get "done", request the download link, and sometimes receive 409 NOT_READY because the gateway had not applied the result yet. That race simply does not exist when the public event is emitted by whoever owns the state.

One subscriber, two queues

notification-service binds to domain.events twice, and the queues are fundamentally different — confusing them means either sending one email per replica, or never delivering status to the browser:

QueueKindWhy
notifications.mail shared, durable, competing consumers The email must go out exactly once, however many replicas run.
notifications.sse.<instance> exclusive, auto-delete, one per replica Every replica receives the event; only the one holding that user's connection pushes it. No sticky routing, no shared Redis.

Delivery guarantees

  • One job at a time per worker. noAck: false, manual ack, prefetchCount: 1. A crash redelivers exactly one job, and load spreads by real capacity rather than round-robin.
  • Durable quorum queues, persistent messages, publisher confirms.
  • Retry with backoff. A retryable failure nacks without requeue and dead-letters into conversion.retry.<n> — a queue with x-message-ttl and a DLX back to the work queue. Three attempts at 10 s / 60 s / 300 s, then conversion.jobs.dlq and FAILED.
  • Idempotency. The job id is the message id. A worker with no database cannot check status, so deduplication lives in the gateway: a repeated result.completed for an already terminal job is a no-op. Re-running the conversion itself is harmless — the result overwrites the same key.
  • Transactional outbox in gateway and identity: the state row and the outbox row are written in one @Transactional() (already available through typeorm-transactional), and a relay publishes them separately. Without it you eventually get a job no worker hears about, or an event for a transaction that rolled back.
  • correlationId travels in message headers and is logged by every service.

05The conversion pipeline

Job state machine

PENDING→ QUEUED→ PROCESSING→ COMPLETED→ EXPIRED
↳ RETRYING↩ PROCESSING · FAILED · CANCELLED ← from PENDING or QUEUED

Every transition is written by the gateway — either from its own HTTP handler or by applying a worker result. Each one appends to job_events: that trail answers "why did this job take four minutes" without digging through logs.

Worker algorithm

Identical for both converters; it lives in libs/worker-kit:

  1. Receive the command. It carries everything needed: jobId, sourceKey, sourceFormat, targetFormat, options, resultKey. There is no database to consult, and none to consult it in.
  2. Stream the source object from S3 into the job's temp directory.
  3. Re-verify the real file type by its signature, not by the extension or the client's Content-Type. A mismatch is INVALID_SOURCE, with no retry.
  4. Resolve a converter from the registry; no match is UNSUPPORTED_CONVERSION, with no retry.
  5. Run it under a hard timeout and a memory ceiling.
  6. Stream the result to S3 at the key from the command; record size and checksum.
  7. Publish result.completed and ack; delete the temp directory in a finally.

Failures are classified retryable (storage timeout, OOM, worker killed) against permanent (corrupt input, unsupported pair, too large). Permanent failures never burn three retries.

The converter registry

Every engine implements one interface and self-registers. The matrix served at GET /formats is derived from the registry — adding a format is one provider and zero changes elsewhere.

export interface Converter {
  readonly id: string;              // 'sharp-image', 'data-canonical'
  supports(source: Format, target: Format): boolean;
  capabilities(): ConversionPair[]; // feeds GET /formats
  convert(input: ConversionInput, ctx: ConversionContext): Promise<ConversionResult>;
}

ConversionContext carries the temp directory, an AbortSignal for the timeout, a progress callback and the logger already bound to the correlation id. The format family is no longer part of the interface: it is decided by whichever service loaded the registry.

06Data conversion

Twelve directions are required between four formats. Not twelve converters. csv, json, xml and yaml are different representations of the same structure, so the right decomposition is a different one:

csv json xml yaml → parse → canonical model → serialize → csv json xml yaml

Four parsers and four serializers — eight pieces of code cover all twelve directions. A fifth format (toml, say) adds eight new directions for the price of two new pieces rather than eight. It also tests separately: a parser is checked for reading correctly, a serializer for writing correctly, with no combinatorial explosion of pairs.

from \ tocsvjsonxmlyaml

json✓*—✓✓
xml✓*✓—✓
yaml✓*✓✓—

The asterisk: not every tree fits in a table

This is the main trap, and it is worth settling before any code is written. csv is a flat table; json, xml and yaml are trees. Going towards a tree is trivial; coming back is not:

// Fits in CSV: an array of flat objects
[{ "id": 1, "name": "Anna" }, { "id": 2, "name": "Boris" }]

// Does not fit: nesting and heterogeneous keys
{ "user": { "name": "Anna", "tags": ["a", "b"] } }

The behaviour is a conversion option, declared in the contract:

  • flatten: false (default) — a document that is not an array of flat objects is rejected with NOT_TABULAR. This is a permanent failure: retrying is pointless, and the user gets a clear reason instead of a broken CSV.
  • flatten: true — nesting is expanded into dotted keys (user.name, user.tags.0), columns are the union across records, gaps are empty.

XML specifics

xml has no single canonical mapping onto json, so the conventions are pinned in options and never change silently: rootName (root element, default root), itemName (element for array entries, default item), attributePrefix (attributes as keys prefixed with @), textKey (text content of a mixed node, default #text). Without those rules xml → json → xml will not return the original document, and that is the first thing a round-trip test checks.

What to test

Round-trips on every pair where one is meaningful: json → yaml → json and json → xml → json must reproduce the original. Plus a set of hostile fixtures: csv with commas and newlines inside quotes, xml with attributes and mixed content, yaml with anchors and block scalars, json nested fifty levels deep, an empty file, a file containing only a BOM.

Streaming

The canonical model does not fit in memory for large files, so parsers and serializers work record-by-record wherever the format allows: csv (line by line) and json arrays (through a streaming parser). yaml and xml are parsed whole, so their input size limit is lower, and that is reflected in the quotas. For the expected volume (files up to a hundred megabytes) this is enough; if more is needed later, only the parsers change, not the contract.

07Storage

  • Two private buckets, uploads/ and results/. No object is ever publicly readable.
  • Keys are <bucket>/<userId>/<jobId>: the user id in the path makes ownership checks cheap and cross-user access structurally impossible.
  • The result key is computed by the gateway and passed in the command — a worker never invents names and cannot write to the wrong place.
  • Lifecycle: the source is deleted after a successful conversion, the result at expires_at (24 h by default) by a scheduled job in the gateway that also marks the rows EXPIRED.

Upload path — presigned PUT, in three steps. The bytes never pass through Node:

  1. POST /conversions — the gateway creates the job as PENDING and returns the jobId with a presigned PUT URL that already pins the object key, the content type and a size ceiling.
  2. The client uploads the file straight to MinIO with that URL.
  3. POST /conversions/:id/uploaded — the gateway does a headObject, confirms the object exists and is within the limit, moves the job to QUEUED and publishes the command.

Download is symmetric: a 302 to a presigned GET valid about five minutes, after the job.user_id check. Node signs URLs and proxies nothing, so file size stops affecting memory and HTTP connection lifetimes.

10Validation

The brief allows zod or Joi; the boilerplate already wires Joi (for env) and ValidationPipe.

Recommendation

nestjs-zod for HTTP DTOs and message payloads, with Joi kept for env validation. One schema in libs/contracts does three jobs: the compile-time type, the guard at the HTTP edge, and the guard at the consumer — the last matters because a message from another service is exactly as untrusted as a request from a browser. It also generates the OpenAPI schema, so documentation cannot drift from validation.

The conversion options are validated separately: flatten, delimiter, rootName, attributePrefix and the rest. Their schema depends on the target format, so in the contract this is a discriminated union on targetFormat — which means you cannot send rootName for csv and have it silently ignored.

11Security

  • Credentials. argon2id for passwords. A short-lived access JWT (15 min) and a rotating refresh token in an httpOnly, SameSite=Strict cookie; reuse detection revokes the whole token family.
  • Token verification is local. The gateway does not call identity-service per request: it verifies the JWT signature with its own key, zero network hops on the hot path. It reaches identity only for register, login, refresh and password reset.
  • Authorization. Every job query is scoped by user_id at the repository level, not by a check a caller might forget. An ADMIN role covers the ops endpoints.
  • File intake. Extension allow-list, signature verification, a hard size limit inside the signature itself, and the filename never becomes a storage key — the key is the job UUID.
  • Parsing is an attack surface too. Each parser has its own holes: xml needs external entities disabled (XXE) and a depth limit, yaml needs a safe loader with no arbitrary tags, json needs a nesting limit. This is not theory — those three are exactly where format converters get broken.
  • Worker isolation. Non-root, read-only root filesystem apart from the temp directory, dropped capabilities, no outbound network, CPU and memory limits, a per-job timeout.
  • Rate limiting. ThrottlerModule globally plus a per-user quota on POST /conversions: N jobs per hour, M concurrent, enforced against the job table.
  • Secrets from env only; .env.example documents every key.

12Observability & testing

  • pino structured logs; the correlation id is generated at the edge and propagated through RMQ headers into every worker log line.
  • Liveness and readiness per service through Terminus. A worker's readiness checks the broker and storage — but not a database, which it does not have.
  • Prometheus metrics: depth of each queue separately, job duration by format pair, failure rate by error code, retries. Queue depth is the autoscaling signal, and there are now two of them.
  • Graceful shutdown: stop consuming, finish the in-flight job, exit.
  • Tests. Parsers and serializers get unit tests on fixtures — cheap, and they cover the bulk of the logic. Round-trip tests on the meaningful pairs. Integration tests per service on Testcontainers (Postgres + RabbitMQ + MinIO). One end-to-end: upload a real csv and wait for correct json on download.
  • CI runs lint, unit, e2e and a docker build per app on every pull request.

13Local stack

One docker compose up brings up PostgreSQL (three databases via an init script — gateway, identity, notification), RabbitMQ with the management UI, MinIO with an mc init container, Mailhog to catch all development mail (no turboSMTP account needed to work), and the five services. Both converters scale through --scale independently of one another — the most direct way to show a reviewer why they were split.

14Roadmap

  1. Phase 0

    Monorepo conversion, libs extracted, compose stack, health checks green across five services.

  2. Phase 1

    identity-service and gateway auth: register, login, refresh, verify; the RPC contract; e2e.

  3. Phase 2

    Happy path through data-service: job → presigned upload → queue → csv → json → result → download. The cheapest way to exercise the whole pipeline, because it needs no binaries and no heavy fixtures.

  4. Phase 3

    The other eleven directions: four parsers, four serializers, the canonical model, flatten, the xml conventions, round-trip tests.

  5. Phase 4

    worker-kit is extracted from data-service, and image-service is built on it with its own queue and its own image — proof that the split is real.

  6. Phase 5

    Reliability: retries and DLQ, outbox, idempotency, cancellation, TTL cleanup.

  7. Phase 6

    notification-service: SSE, history, auth mail.

  8. Phase 7

    Hardening: quotas, metrics, Testcontainers, CI, README and Swagger.

The order is deliberate: data-service comes first precisely because it is the lightest — the transport, the storage and the job model are all proven against a conversion you can write in an evening. By the time image-service appears, there is nothing left to get wrong.

15Open questions

  1. Which image directions? The data side is fixed; images are not. Proposal: png, jpeg, webp, avif, tiff in all directions plus resize as an option — on sharp that is as much work as a single direction.
  2. Maximum file size and result retention — 100 MB and 24 h are placeholders. yaml and xml need a lower limit: they are parsed whole into memory.
  3. Default flatten behaviour: reject a non-tabular document, or expand it with dotted keys? The document currently says reject.
  4. Must a user verify their email before converting?
  5. Is an admin surface in scope — all jobs, requeue, statistics?
  6. Expected load target: it decides whether quorum queues and the outbox are necessary or gold-plating.

2. The gateway creates the job and signs the upload

// apps/api-gateway/src/modules/conversions/conversions.service.ts
async create(userId: string, dto: CreateConversionDto) {
  const job = await this.jobs.save(this.jobs.create({
    userId,
    status: JobStatus.PENDING,
    sourceFormat: dto.sourceFormat,
    targetFormat: dto.targetFormat,
    options: dto.options,
    sourceKey: `${userId}/${randomUUID()}`,
    resultKey: `${userId}/${randomUUID()}.${dto.targetFormat}`,
  }));

  // The signature pins the key, the type and the size ceiling.
  const uploadUrl = await this.storage.presignPut({
    bucket: Bucket.Uploads,
    key: job.sourceKey,
    contentType: dto.contentType,
    maxBytes: limitFor(dto.sourceFormat),   // lower for yaml and xml
    expiresIn: 900,
  });

  return { jobId: job.id, uploadUrl, expiresIn: 900 };
}

@Transactional()                        // job row and outbox row in one transaction
async confirmUpload(userId: string, jobId: string) {
  const job = await this.jobs.findOneByOrFail({ id: jobId, userId });
  if (job.status !== JobStatus.PENDING) return { status: job.status };

  const head = await this.storage.head(Bucket.Uploads, job.sourceKey);
  if (!head) throw new BadRequestException('SOURCE_NOT_UPLOADED');

  job.status = JobStatus.QUEUED;
  job.sourceSize = head.size;
  await this.jobs.save(job);

  // The family picks the queue — and this is the only place
  // that knows there is more than one converter.
  await this.outbox.save({
    exchange: 'conversion.commands',
    routingKey: `convert.${familyOf(job.targetFormat)}`,   // image | data
    payload: {
      jobId: job.id,
      sourceKey: job.sourceKey,
      resultKey: job.resultKey,
      sourceFormat: job.sourceFormat,
      targetFormat: job.targetFormat,
      options: job.options,
    },
  });

  return { status: job.status };
}

3. The gateway applies the result, then emits the public event

// apps/api-gateway/src/modules/conversions/results.consumer.ts
@EventPattern('result.completed')
@Transactional()
async onCompleted(@Payload() evt: ResultCompleted) {
  const job = await this.jobs.findOneByOrFail({ id: evt.jobId });
  if (isTerminal(job.status)) return;     // idempotency lives here

  job.status = JobStatus.COMPLETED;
  job.resultSize = evt.size;
  job.checksum = evt.checksum;
  job.finishedAt = new Date();
  await this.jobs.save(job);

  // The public event is emitted AFTER the state is committed —
  // otherwise the client gets an SSE "done" before the link works.
  await this.outbox.save({
    exchange: 'domain.events',
    routingKey: 'conversion.completed',
    payload: { jobId: job.id, userId: job.userId },
  });

  await this.storage.delete(Bucket.Uploads, job.sourceKey);   // source no longer needed
}

4. The worker: one core, different registries

// libs/worker-kit/src/conversion.handler.ts — one for both services
async handle(msg: ConversionRequested, ctx: RmqContext) {
  const channel = ctx.getChannelRef();
  const raw = ctx.getMessage();
  const dir = await mkdtemp(join(tmpdir(), `job-${msg.jobId}-`));

  try {
    const source = join(dir, 'source');
    await pipeline(
      await this.storage.getStream(Bucket.Uploads, msg.sourceKey),
      createWriteStream(source),
    );

    const real = await sniffFormat(source);          // by signature, not extension
    if (real !== msg.sourceFormat) throw new PermanentError('INVALID_SOURCE');

    const converter = this.registry.resolve(msg.sourceFormat, msg.targetFormat);
    if (!converter) throw new PermanentError('UNSUPPORTED_CONVERSION');

    const out = await converter.convert(
      { path: source, options: msg.options },
      { dir, signal: AbortSignal.timeout(JOB_TIMEOUT_MS), logger: this.logger },
    );

    await this.storage.put(Bucket.Results, msg.resultKey, createReadStream(out.path));

    // Not a single database query in the whole handler — there is no database.
    await this.publisher.emit('result.completed', {
      jobId: msg.jobId, size: out.size, checksum: out.checksum,
    });

    channel.ack(raw);
  } catch (err) {
    await this.failures.handle(msg, err, channel, raw);   // permanent → result.failed, else → DLX
  } finally {
    await rm(dir, { recursive: true, force: true });
  }
}

5. Twelve directions out of eight pieces

// apps/data-service/src/converters/data.converter.ts
export interface DataParser {
  readonly format: DataFormat;
  parse(input: Readable, opts: ParseOptions): Promise<CanonicalDocument>;
}

export interface DataSerializer {
  readonly format: DataFormat;
  serialize(doc: CanonicalDocument, opts: SerializeOptions): Readable;
}

@Injectable()
export class DataConverter implements Converter {
  readonly id = 'data-canonical';

  constructor(
    @Inject(PARSERS) private readonly parsers: DataParser[],
    @Inject(SERIALIZERS) private readonly serializers: DataSerializer[],
  ) {}

  // The matrix is the cartesian product minus the identity pairs.
  // 4 + 4 providers give all 12 directions.
  capabilities(): ConversionPair[] {
    return this.parsers.flatMap((p) =>
      this.serializers
        .filter((s) => s.format !== p.format)
        .map((s) => ({ from: p.format, to: s.format })),
    );
  }

  async convert(input: ConversionInput, ctx: ConversionContext) {
    const parser = this.parsers.find((p) => p.format === input.sourceFormat)!;
    const serializer = this.serializers.find((s) => s.format === input.targetFormat)!;

    const doc = await parser.parse(createReadStream(input.path), input.options);

    // The one place where trees meet tables.
    if (serializer.format === DataFormat.Csv && !doc.isTabular) {
      if (!input.options.flatten) throw new PermanentError('NOT_TABULAR');
      doc.flatten({ separator: '.' });
    }

    const out = join(ctx.dir, 'result');
    await pipeline(serializer.serialize(doc, input.options), createWriteStream(out));
    return { path: out, size: (await stat(out)).size };
  }
}

Adding toml is a TomlParser, a TomlSerializer and two lines in the providers. Eight new directions appear in GET /formats on their own, because the matrix is computed rather than written by hand.

6. notification-service and its two queues

// apps/notification-service/src/main.ts
const app = await NestFactory.create(NotificationModule);   // HTTP: holds the SSE connections

// (1) Mail — a shared durable queue: the email goes out ONCE.
app.connectMicroservice<MicroserviceOptions>({
  transport: Transport.RMQ,
  options: {
    urls: [process.env.RABBITMQ_URL],
    queue: 'notifications.mail',
    queueOptions: { durable: true },
    noAck: false,
  },
});

// (2) SSE — its OWN exclusive queue per replica.
app.connectMicroservice<MicroserviceOptions>({
  transport: Transport.RMQ,
  options: {
    urls: [process.env.RABBITMQ_URL],
    queue: `notifications.sse.${process.env.HOSTNAME}`,
    queueOptions: { durable: false, exclusive: true, autoDelete: true },
  },
});

ConnectionHub inside is just a Map<userId, Subject>. A replica holding no connection for that user quietly ignores the event, so neither sticky routing nor a shared Redis is needed.
