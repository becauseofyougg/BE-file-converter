01 · Two load-bearing decisions

HTTP requests never
do the conversion

record job→ presigned URL→ client PUTs to S3→ 202→ queue→ worker

And the second, no less important: the gateway owns the jobs, and the workers have no database. That is why there can be two converters, or three, or five, without the data model changing.

02 · Decomposition

Five services

api-gateway

The only REST surface. Local JWT, presigned URLs, and it owns the jobs: creates them, consumes results, writes status.

gateway DB

identity-service

Registration, login, JWT and refresh, email verification, password reset.

identity DB

image-service

Images on sharp. A light image with no external binaries.

no DB · CPU · ×N

data-service

csv, json, xml, yaml — all 12 directions. Pure Node.

no DB · CPU · ×N

notification-service

Browsers' SSE connections, notification history, auth mail.

notification DB

The second converter was called "the text service" in discussion. Here it is data-service: it handles structured text formats, not documents. docx → pdf would be a third service with its own image.

02 · Rationale

Why the boundary falls here

  • 01Between the converters, the split is by image weight, not domain. image-service carries only sharp. Any heavyweight engine added later brings hundreds of megabytes — to its own service, leaving the others untouched.
  • 02Auth is split out to keep the gateway free of user-table coupling.
  • 03Notifications are split out because a live SSE connection costs memory and a connection slot, not CPU.
  • —A job cannot have two owners. The job list must be one paginated query, not a merge across sources — so conversion_jobs lives in the gateway's DB and the workers never touch a database.

03 · Repository

A shared worker core is mandatory

apps/
  api-gateway/            // REST + owner of the jobs
  identity-service/       // RMQ request/response
  image-service/          // RMQ consumer, sharp
  data-service/           // RMQ consumer, csv/json/xml/yaml
  notification-service/   // SSE + history + SMTP
libs/
  core/ contracts/ storage/ observability/
  worker-kit/             // download → verify → convert → upload

Both converters do the same thing and differ only in the converter registry. Without worker-kit you get two nearly identical services — the first thing a reviewer will pick on.

04 · Messaging

Three exchanges, three roles

conversion.commands

convert.image and convert.data — two queues, two deployments, two images.

conversion.results

The worker reports result.completed. Only the gateway listens.

domain.events

Public events. notification-service binds two queues: shared for mail, exclusive-per-replica for SSE.

Why results go through the gateway. The public conversion.completed is emitted only after the state is committed. Otherwise the user gets an SSE "done", requests the link, and catches a 409 NOT_READY because the status has not been applied yet.

04 · Reliability

Delivery guarantees

  • 01One job at a time per worker. prefetchCount: 1, manual ack. A crash redelivers exactly one job.
  • 02Idempotency lives in the gateway. A worker with no database cannot check status — but a repeated result.completed for a finished job is a no-op.
  • 03Transactional outbox in gateway and identity: the state row and the outbox row in one transaction.
attempt 1→ +10 s→ +60 s→ +300 s→ DLQ · FAILED

Permanent failures — corrupt input, unsupported pair, NOT_TABULAR — never burn three attempts.

05 · Pipeline

Only the gateway writes status

PENDING→ QUEUED→ PROCESSING→ COMPLETED→ EXPIRED
↳ RETRYING↩ · FAILED · CANCELLED

Every transition appends to job_events — the trail that answers "why did this job take four minutes" without digging through logs.

The worker makes no database query at all. The command already carries everything: sourceKey, resultKey, formats, options. It re-verifies the file type by signature, never by extension.

06 · Data

Twelve directions out of eight pieces

csvjsonxmlyaml → parse → canonical model → serialize → csvjsonxmlyaml

csv, json, xml and yaml are different representations of one structure. So not twelve converters — four parsers and four serializers.

A fifth format adds eight new directions for two pieces instead of eight. Testing splits too: a parser is checked for reading correctly, a serializer for writing correctly, with no combinatorial explosion. The GET /formats matrix is computed, not hand-written.

06 · The trap

Not every tree fits in a table

// Fits in CSV: an array of flat objects
[{ "id": 1, "name": "Anna" }, { "id": 2, "name": "Boris" }]

// Does not fit: nesting and heterogeneous keys
{ "user": { "name": "Anna", "tags": ["a", "b"] } }

flatten: false — default

The document is rejected with NOT_TABULAR. A permanent failure: the user gets a clear reason instead of a broken CSV.

flatten: true

Nesting expands into dotted keys: user.name, user.tags.0.

xml has its own conventions — rootName, itemName, attributePrefix, textKey. Without them xml → json → xml will not return the original, and that is the first thing a round-trip test checks.

07 · Storage

Bytes never pass through Node at all

  • 01Upload is a presigned PUT in three steps: POST /conversions returns the URL, the client sends the file straight to MinIO, POST /:id/uploaded confirms the object with headObject and queues it.
  • 02The signature pins the key, the type and a size ceiling. Lower for yaml and xml — they parse whole into memory.
  • 03Download is a 302 to a presigned GET after the job.user_id check. The result key is computed by the gateway: a worker cannot write to the wrong place.
  • 04The source is deleted after a successful conversion, the result at expires_at.

11 · Security

Parsing is an attack surface too

Parsers

xml needs external entities disabled (XXE) and a depth limit. yaml needs a safe loader with no arbitrary tags. json needs a nesting limit. Those three are exactly where format converters get broken.

Worker isolation

Non-root, read-only filesystem apart from the temp dir, dropped capabilities, no outbound network, CPU and memory limits, a per-job timeout.

Credentials

argon2id, 15-minute access JWT, rotating refresh in an httpOnly cookie. The signature is verified locally in the gateway.

File intake

Extension allow-list, signature verification, a size limit inside the signature itself. The filename never becomes a storage key — the key is the job UUID.

14 · Roadmap

data-service comes first

PhaseContent
0Monorepo, libs, compose stack, health checks across five services
1identity-service and gateway auth, the RPC contract, e2e
2Happy path through data-service: job → presigned → queue → csv → json → download
3The other 11 directions: parsers, serializers, flatten, xml conventions, round-trips
4worker-kit extracted, image-service built on it — proof the split is real
5Reliability: retries and DLQ, outbox, idempotency, cancellation, TTL
6notification-service: SSE, history, auth mail
7Hardening: quotas, metrics, Testcontainers, CI, Swagger

The order is deliberate: data-service is the lightest, so the transport, the storage and the job model are all proven against a conversion you can write in an evening. By the time image-service appears, there is nothing left to get wrong.

15 · What needs deciding

Open questions

  1. Which image directions? The data side is fixed; images are not. Proposal: png, jpeg, webp, avif, tiff in all directions plus resize — on sharp that is as much work as a single direction.
  2. Maximum file size and retention — 100 MB and 24 h are placeholders; yaml and xml need a lower limit.
  3. Default flatten: reject a non-tabular document, or expand it with dotted keys?
  4. Must a user verify their email before converting?
  5. Is an admin surface in scope — all jobs, requeue, statistics?
  6. Expected load target: it decides whether quorum queues and the outbox are necessary.
