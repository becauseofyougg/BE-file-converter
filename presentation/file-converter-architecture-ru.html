01Кратко

Сервис принимает файл, асинхронно конвертирует его в другой формат и отдаёт результат. Gateway создаёт задачу и выдаёт presigned-ссылку, клиент льёт файл прямо в хранилище, команда уходит в очередь, её забирает воркер нужного семейства форматов.

Два решения держат на себе всю конструкцию:

  1. HTTP-запрос никогда не конвертирует. Это позволяет тяжёлому файлу и медленному движку сосуществовать, не удерживая соединение открытым, и даёт разбиению на микросервисы настоящий смысл, а не декоративный.
  2. Задачами владеет gateway, воркеры не имеют своей БД. Воркер — чистый вычислитель: получил команду, скачал, сконвертировал, залил, отчитался событием. Поэтому конвертеров может быть два, три или пять, и модель данных от этого не меняется.

02Разбиение на сервисы

СервисОтветственностьВладеет БДМасштабируется по
api-gateway Единственная точка REST. Проверяет JWT локально, выдаёт presigned-ссылки, владеет задачами конвертации: создаёт их, слушает результаты воркеров и пишет статус. Rate limiting, квоты, OpenAPI. gateway конкурентности HTTP
identity-service Регистрация, вход, выдача и обновление JWT, подтверждение email, сброс пароля, профиль. identity низко
image-service Конвертация изображений на sharp. Stateless, N реплик, лёгкий образ без внешних бинарников. — CPU
data-service Конвертация структурированных данных: csv, json, xml, yaml — все 12 направлений. Stateless, N реплик, чистый Node. — CPU
notification-service Доставка уведомлений: держит SSE-соединения браузеров и пушит статус задач, ведёт историю, отправляет auth-письма по SMTP. notification числу живых соединений

Про имя. В обсуждении второй конвертер назывался «текстовым». Здесь он называется data-service, потому что работает со структурированными текстовыми форматами, а не с документами: если позже появятся docx → pdf, это будет третий сервис со своим образом и своей очередью, а не расширение этого.

Почему граница проходит именно здесь

  • Между конвертерами — по ресурсам образа, а не по домену. image-service несёт только sharp, и его образ лёгкий. Любой тяжёлый движок, который появится позже (LibreOffice, ffmpeg), добавит сотни мегабайт — и добавит их своему сервису, не задев остальные. Сорокаминутное видео не должно блокировать ресайз превью на 200 мс, и разные очереди с разными деплойментами — единственный способ это гарантировать.
  • Аутентификация вынесена, чтобы gateway не был связан с таблицей пользователей и чтобы получить чистый пример синхронного вызова поверх брокера.
  • Нотификации вынесены, потому что живое SSE-соединение — это память и счётчик коннектов, а не CPU. Тысяча ждущих вкладок и тысяча REST-запросов в секунду нагружают процесс по-разному, и масштабировать их надо независимо.
Ключевое следствие

Раз конвертеров несколько, у задачи не может быть двух владельцев: список задач пользователя должен быть одним запросом с пагинацией, а не склейкой из нескольких источников. Поэтому conversion_jobs живёт в БД gateway, а воркеры не ходят в базу вообще. Добавление третьего конвертера не требует ни одной миграции.

03Структура репозитория

Режим Nest monorepo, в текущем репозитории. Существующие модули src/core/* переезжают в libs/core и импортируются каждым приложением без изменений.

apps/
  api-gateway/            // REST + владелец задач
  identity-service/       // RMQ-хендлеры, request/response
  image-service/          // RMQ-консьюмер, sharp
  data-service/           // RMQ-консьюмер, csv/json/xml/yaml
  notification-service/   // SSE + история + SMTP
libs/
  core/                   // config, database, health, throttler (перенос из src/core)
  contracts/              // сообщения, payload'ы, схемы, коды ошибок, матрица форматов
  worker-kit/             // ОБЩЕЕ ядро воркера: скачать → проверить → конвертировать → залить
  storage/                // клиент S3: put, get stream, presign, delete
  observability/          // pino-логгер, correlation-id, метрики
Почему worker-kit обязателен

Оба конвертера делают одно и то же: скачать из S3, проверить сигнатуру, сконвертировать, залить результат, отчитаться событием, убрать за собой временный каталог. Различается только реестр конвертеров. Без общей библиотеки получатся два почти одинаковых сервиса — и это первое, за что зацепится ревьюер. С ней image-service и data-service — это тонкая обвязка: свой набор провайдеров и имя очереди.

Шаги перехода от текущего boilerplate

  1. nest-cli.json → режим monorepo, записи projects для пяти приложений и пяти библиотек.
  2. git mv src/core libs/core; заготовки src/modules/* расходятся по приложениям.
  3. Пути в tsconfig.json: @core/*, @contracts/*, @worker-kit/*, @storage/*.
  4. Разделить main.ts: gateway сохраняет текущий bootstrap на Fastify (compression, cookies, CORS, validation pipe, transactional context); воркеры используют NestFactory.createMicroservice с Transport.RMQ плюс минимальный HTTP-listener только для /health.
  5. Интерфейс Config расширяется под каждое приложение: воркеру не нужны ни SMTP-креды, ни строка подключения к БД — только RabbitMQ и S3.
  6. Миграции есть только у трёх приложений с БД: gateway, identity, notification.

04Обмен сообщениями

Транспорт — @nestjs/microservices поверх RabbitMQ. Три exchange, и роли у них разные.

Почему результат идёт через gateway, а не сразу к пользователю

Воркер публикует result.completed — это внутренний факт: «файл сконвертирован, результат лежит по такому ключу». Gateway применяет его к своей таблице и только после коммита публикует уже публичное событие conversion.completed в domain.events, откуда его забирает notification-service и пушит в браузер.

Лишний хоп здесь окупается: если бы SSE пушился напрямую из события воркера, пользователь получил бы «готово», дёрнул бы ссылку на скачивание и с некоторой вероятностью получил 409 NOT_READY, потому что gateway ещё не применил результат. Такой гонки просто нет, если наружу событие выпускает тот, кто владеет состоянием.

Две очереди у notification-service

Сервис подписывается на domain.events дважды, и очереди принципиально разные — перепутать их значит либо разослать письмо по числу реплик, либо не доставить статус в браузер:

ОчередьТипЗачем
notifications.mail общая, durable, конкурирующие консьюмеры Письмо должно уйти ровно один раз, сколько бы реплик ни работало.
notifications.sse.<instance> эксклюзивная, auto-delete, по одной на реплику Событие получают все реплики, а пушит только та, что держит соединение этого пользователя. Не нужна ни sticky-маршрутизация, ни общий Redis.

Гарантии доставки

  • Одна задача за раз на воркер. noAck: false, ручной ack, prefetchCount: 1. Падение переотправляет ровно одну задачу, а нагрузка расходится по фактической пропускной способности, а не round-robin.
  • Durable quorum-очереди, persistent-сообщения, publisher confirms.
  • Повторы с задержкой. Retryable-ошибка даёт nack без requeue и уводит сообщение в conversion.retry.<n> — очередь с x-message-ttl и DLX обратно в рабочую. Три попытки через 10 с / 60 с / 300 с, затем conversion.jobs.dlq и статус FAILED.
  • Идемпотентность. Id задачи выступает message id. Воркер без БД не может проверить статус, поэтому дедупликация живёт в gateway: повторный result.completed по уже завершённой задаче — no-op. Повторная конвертация того же файла безвредна: результат перезаписывается по тому же ключу.
  • Transactional outbox в gateway и identity: строка состояния и строка outbox пишутся в одной @Transactional() (уже доступно через typeorm-transactional), relay публикует их отдельно. Без этого рано или поздно появится задача, о которой ни один воркер не узнал, или событие о транзакции, которая откатилась.
  • correlationId едет в заголовках сообщения и попадает в логи каждого сервиса.

05Пайплайн конвертации

Машина состояний задачи

PENDING→ QUEUED→ PROCESSING→ COMPLETED→ EXPIRED
↳ RETRYING↩ PROCESSING · FAILED · CANCELLED ← из PENDING или QUEUED

Все переходы пишет gateway — либо из своего HTTP-обработчика, либо применяя результат воркера. Каждый переход добавляет строку в job_events: этот журнал отвечает на вопрос «почему задача шла четыре минуты» без раскопок в логах.

Алгоритм воркера

Одинаковый для обоих конвертеров, живёт в libs/worker-kit:

  1. Получить команду. В ней всё необходимое: jobId, sourceKey, sourceFormat, targetFormat, options, resultKey. В базу идти не нужно и некуда.
  2. Стримом скачать исходный объект из S3 во временный каталог задачи.
  3. Перепроверить настоящий тип файла по сигнатуре, а не по расширению или Content-Type от клиента. Несовпадение — INVALID_SOURCE, без повторов.
  4. Найти конвертер в реестре; если совпадения нет — UNSUPPORTED_CONVERSION, без повторов.
  5. Запустить его с жёстким таймаутом и ограничением по памяти.
  6. Стримом записать результат в S3 по ключу из команды, посчитать размер и чек-сумму.
  7. Опубликовать result.completed и сделать ack; в finally удалить временный каталог.

Ошибки делятся на retryable (таймаут хранилища, OOM, убитый воркер) и permanent (битый вход, неподдерживаемая пара форматов, слишком большой файл). Permanent-ошибки не тратят три попытки впустую.

Реестр конвертеров

Каждый движок реализует один интерфейс и сам себя регистрирует. Матрица, которую отдаёт GET /formats, строится из реестра — добавление формата это один провайдер и ноль изменений в остальном коде.

export interface Converter {
  readonly id: string;              // 'sharp-image', 'data-tabular'
  supports(source: Format, target: Format): boolean;
  capabilities(): ConversionPair[]; // питает GET /formats
  convert(input: ConversionInput, ctx: ConversionContext): Promise<ConversionResult>;
}

ConversionContext несёт временный каталог, AbortSignal для таймаута, колбэк прогресса и логгер, уже привязанный к correlation id. Семейство формата больше не хранится в интерфейсе: его определяет сервис, который поднял этот реестр.

06Конвертация данных

Требуется 12 направлений между четырьмя форматами. Не 12 конвертеров. Csv, json, xml и yaml — это разные представления одной и той же структуры, поэтому правильная декомпозиция другая:

csv json xml yaml → parse → каноническая модель → serialize → csv json xml yaml

4 парсера и 4 сериализатора — 8 кусков кода закрывают все 12 направлений. Пятый формат (скажем, toml) добавит сразу 8 новых направлений ценой двух новых кусков, а не восьми. И тестируется это тоже по отдельности: парсер проверяется на «прочитал ли правильно», сериализатор — на «записал ли правильно», без комбинаторного взрыва пар.

из \ вcsvjsonxmlyaml
csv—✓✓✓
json✓*—✓✓
xml✓*✓—✓
yaml✓*✓✓—

Звёздочка: не всякое дерево ложится в таблицу

Это главный подводный камень, и его стоит проговорить до начала работы. Csv — плоская таблица, а json, xml и yaml — деревья. В сторону дерева всё просто, обратно — нет:

// Ложится в CSV: массив плоских объектов
[{ "id": 1, "name": "Анна" }, { "id": 2, "name": "Борис" }]

// Не ложится: вложенность и разнородные ключи
{ "user": { "name": "Анна", "tags": ["a", "b"] } }

Поведение задаётся опцией конвертации и описано в контракте:

  • flatten: false (по умолчанию) — документ, который не является массивом плоских объектов, отклоняется с NOT_TABULAR. Это permanent-ошибка: повторять её бессмысленно, и пользователь получает внятную причину, а не битый CSV.
  • flatten: true — вложенность разворачивается в ключи через точку (user.name, user.tags.0), объединение колонок по всем записям, пропуски пустые.

Особенности XML

У xml нет однозначного отображения на json, поэтому конвенции фиксируются в опциях и не меняются молча: rootName (корневой элемент, по умолчанию root), itemName (элемент для массива, по умолчанию item), attributePrefix (атрибуты как ключи с префиксом @), textKey (текстовое содержимое смешанного узла, по умолчанию #text). Без этих правил xml → json → xml не даст исходный документ, и это первое, что проверит тест на round-trip.

Что тестировать

Round-trip на каждую пару, где он осмыслен: json → yaml → json и json → xml → json должны давать исходный документ. Плюс набор «злых» фикстур: csv с запятыми и переводами строк внутри кавычек, xml с атрибутами и смешанным содержимым, yaml с якорями и многострочными блоками, json глубиной 50 уровней, пустой файл, файл из одного BOM.

Потоковость

Каноническая модель для больших файлов целиком в памяти не помещается, поэтому парсеры и сериализаторы работают с потоком записей там, где формат это позволяет: csv (построчно) и json-массив (через потоковый парсер). Yaml и xml разбираются целиком — для них лимит размера входа ниже, и это отражено в квотах. Для учебного объёма (файлы до сотни мегабайт) этого достаточно; если понадобится больше, менять придётся только парсеры, а не контракт.

07Хранилище

  • Два приватных бакета, uploads/ и results/. Ни один объект никогда не доступен публично.
  • Ключи вида <bucket>/<userId>/<jobId>: id пользователя в пути делает проверку владения дешёвой, а доступ к чужому файлу структурно невозможным.
  • Ключ результата вычисляет gateway и кладёт в команду — воркер не придумывает имена и не может записать не туда.
  • Жизненный цикл: исходник удаляется после успешной конвертации, результат — по expires_at (24 ч по умолчанию) плановой задачей в gateway, которая же помечает записи EXPIRED.

Путь загрузки — presigned PUT, в три шага. Байты не проходят через Node ни разу:

  1. POST /conversions — gateway создаёт задачу в статусе PENDING и возвращает jobId вместе с presigned PUT-ссылкой, у которой уже зашиты ключ объекта, тип контента и лимит размера.
  2. Клиент льёт файл прямо в MinIO по этой ссылке.
  3. POST /conversions/:id/uploaded — gateway делает headObject, убеждается, что объект есть и укладывается в лимит, переводит задачу в QUEUED и публикует команду.

Скачивание симметрично: 302 на presigned GET со временем жизни около пяти минут, после проверки job.user_id. Итого Node выдаёт подписи и ничего не проксирует, поэтому размер файла перестаёт влиять на память и на время жизни HTTP-соединений.

Второй вход: notification-service

Живое соединение не проходит через gateway — иначе оно висело бы на обоих сервисах сразу и память платилась бы дважды. На ingress это отдельный маршрут (или поддомен events.), а JWT проверяется тем же публичным ключом.

10Валидация

Задание допускает zod или Joi; в boilerplate уже подключены Joi (для env) и ValidationPipe.

Рекомендация

nestjs-zod для HTTP-DTO и для payload'ов сообщений, Joi остаётся на валидации env. Одна схема в libs/contracts делает три дела: тип на этапе компиляции, проверка на HTTP-границе и проверка на стороне консьюмера — последнее важно, потому что сообщение от другого сервиса ровно настолько же недоверенное, как запрос из браузера. Плюс из неё генерируется схема OpenAPI, поэтому документация не может разойтись с валидацией.

Отдельно валидируются опции конвертации: flatten, delimiter, rootName, attributePrefix и прочее. Их схема зависит от целевого формата, поэтому в контракте это discriminated union по targetFormat — тогда нельзя прислать rootName для csv и получить молча проигнорированное поле.

11Безопасность

  • Учётные данные. argon2id для паролей. Короткоживущий access JWT (15 мин) и ротируемый refresh в httpOnly-cookie с SameSite=Strict; обнаружение повторного использования refresh-токена отзывает всё семейство.
  • Проверка токена — локальная. Gateway не ходит в identity-service на каждый запрос: он проверяет подпись JWT своим ключом, без единого сетевого вызова на горячем пути. В identity он обращается только на register, login, refresh и сброс пароля.
  • Авторизация. Любой запрос задач ограничен по user_id на уровне репозитория, а не проверкой, которую вызывающий может забыть. Роль ADMIN покрывает ops-эндпоинты.
  • Приём файлов. Allow-list расширений, проверка по сигнатуре, жёсткий лимит размера в самой подписи, имя файла никогда не становится ключом в хранилище — ключ это UUID задачи.
  • Разбор данных — это тоже атака. У парсеров свои дыры: xml требует отключённых внешних сущностей (XXE) и лимита глубины, yaml — безопасного загрузчика без произвольных тегов, json — лимита вложенности. Это не теория: именно на этих трёх местах ломают конвертеры форматов.
  • Изоляция воркеров. Non-root, read-only корневая ФС кроме временного каталога, сброшенные capabilities, без сети наружу, лимиты CPU и памяти, таймаут на задачу.
  • Rate limiting. ThrottlerModule глобально плюс персональная квота на POST /conversions: N задач в час, M одновременно, проверяется по таблице задач.
  • Секреты только из env; .env.example документирует каждый ключ.

12Наблюдаемость и тесты

  • Структурированные логи через pino; correlation id генерируется на границе и передаётся через заголовки RMQ в каждую строку логов воркера.
  • Liveness и readiness на каждый сервис через Terminus. У воркеров readiness проверяет брокер и хранилище — но не БД, которой у них нет.
  • Метрики Prometheus: глубина каждой очереди отдельно, длительность задачи по паре форматов, доля ошибок по коду, повторы. Глубина очереди — сигнал для автоскейлинга, и теперь их две.
  • Graceful shutdown: перестать читать очередь, докончить текущую задачу, выйти.
  • Тесты. Парсеры и сериализаторы — unit-тестами на фикстурах, это дёшево и покрывает основную логику. Round-trip тесты на осмысленные пары. Интеграционные тесты на сервис против Testcontainers (Postgres + RabbitMQ + MinIO). Один end-to-end: загрузить настоящий csv и дождаться корректного json на скачивании.
  • CI прогоняет lint, unit, e2e и docker build каждого приложения на каждый PR.

13Локальный стек

Один docker compose up поднимает PostgreSQL (три базы через init-скрипт — gateway, identity, notification), RabbitMQ с management UI, MinIO с init-контейнером mc, Mailhog для перехвата почты в разработке (аккаунт turboSMTP для работы не нужен) и пять сервисов. Оба конвертера масштабируются через --scale независимо друг от друга — это самый наглядный способ показать ментору, зачем их разделили.

14План работ

  1. Фаза 0

    Перевод в monorepo, вынос библиотек, compose-стек, зелёные health-check'и на пяти сервисах.

  2. Фаза 1

  3. Фаза 2

    Happy path через data-service: задача → presigned-загрузка → очередь → csv → json → результат → скачивание. Это самый дешёвый способ прогнать весь пайплайн, потому что не нужны ни бинарники, ни тяжёлые фикстуры.

  4. Фаза 3

    Остальные 11 направлений: 4 парсера, 4 сериализатора, канонич­еская модель, flatten, конвенции xml, round-trip тесты.

  5. Фаза 4

    worker-kit выделяется из data-service, на нём поднимается image-service со своей очередью и своим образом — проверка, что разделение настоящее.

  6. Фаза 5

    Надёжность: повторы и DLQ, outbox, идемпотентность, отмена, очистка по TTL.

  7. Фаза 6

    notification-service: SSE, история, auth-письма.

  8. Фаза 7

    Упрочнение: квоты, метрики, Testcontainers, CI, README и Swagger.

Порядок не случаен: data-service идёт первым именно потому, что он самый лёгкий — весь транспорт, хранилище и модель задач проверяются на конвертации, которую можно написать за вечер. К моменту, когда появляется image-service, ошибаться уже негде.

15Открытые вопросы

  1. Какие направления у изображений? Данные зафиксированы, картинки — нет. Предлагаю png, jpeg, webp, avif, tiff во всех направлениях плюс ресайз как опцию: на sharp это столько же работы, сколько одно направление.
  2. Максимальный размер файла и срок хранения результата — 100 МБ и 24 ч пока заглушки. Для yaml и xml лимит должен быть ниже: они разбираются целиком в память.
  3. Поведение flatten по умолчанию: отклонять невыровненный документ или разворачивать через точку? Сейчас в документе — отклонять.

  5. Входит ли в скоуп админский раздел — все задачи, переотправка, статистика?

async create(userId: string, dto: CreateConversionDto) {
  const job = await this.jobs.save(this.jobs.create({
    userId,
    status: JobStatus.PENDING,
    sourceFormat: dto.sourceFormat,
    targetFormat: dto.targetFormat,
    options: dto.options,
    sourceKey: `${userId}/${randomUUID()}`,
    resultKey: `${userId}/${randomUUID()}.${dto.targetFormat}`,
  }));

  // Подпись фиксирует ключ, тип и предельный размер.
  const uploadUrl = await this.storage.presignPut({
    bucket: Bucket.Uploads,
    key: job.sourceKey,
    contentType: dto.contentType,
    maxBytes: limitFor(dto.sourceFormat),   // у yaml и xml он ниже
    expiresIn: 900,
  });

  return { jobId: job.id, uploadUrl, expiresIn: 900 };
}

@Transactional()                        // задача и outbox — одной транзакцией
async confirmUpload(userId: string, jobId: string) {
  const job = await this.jobs.findOneByOrFail({ id: jobId, userId });
  if (job.status !== JobStatus.PENDING) return { status: job.status };

  const head = await this.storage.head(Bucket.Uploads, job.sourceKey);
  if (!head) throw new BadRequestException('SOURCE_NOT_UPLOADED');

  job.status = JobStatus.QUEUED;
  job.sourceSize = head.size;
  await this.jobs.save(job);

  // Семейство определяет очередь — и это единственное место,
  // которое знает, что конвертеров несколько.
  await this.outbox.save({
    exchange: 'conversion.commands',
    routingKey: `convert.${familyOf(job.targetFormat)}`,   // image | data
    payload: {
      jobId: job.id,
      sourceKey: job.sourceKey,
      resultKey: job.resultKey,
      sourceFormat: job.sourceFormat,
      targetFormat: job.targetFormat,
      options: job.options,
    },
  });

  return { status: job.status };
}

3. Gateway применяет результат и только потом выпускает событие наружу

// apps/api-gateway/src/modules/conversions/results.consumer.ts
@EventPattern('result.completed')
@Transactional()
async onCompleted(@Payload() evt: ResultCompleted) {
  const job = await this.jobs.findOneByOrFail({ id: evt.jobId });
  if (isTerminal(job.status)) return;     // идемпотентность живёт здесь

  job.status = JobStatus.COMPLETED;
  job.resultSize = evt.size;
  job.checksum = evt.checksum;
  job.finishedAt = new Date();
  await this.jobs.save(job);

  // Публичное событие выпускается ПОСЛЕ коммита состояния —
  // иначе клиент получит SSE «готово» раньше, чем ссылка начнёт работать.
  await this.outbox.save({
    exchange: 'domain.events',
    routingKey: 'conversion.completed',
    payload: { jobId: job.id, userId: job.userId },
  });

  await this.storage.delete(Bucket.Uploads, job.sourceKey);   // исходник больше не нужен
}

// libs/worker-kit/src/conversion.handler.ts — один на оба сервиса
async handle(msg: ConversionRequested, ctx: RmqContext) {
  const channel = ctx.getChannelRef();
  const raw = ctx.getMessage();
  const dir = await mkdtemp(join(tmpdir(), `job-${msg.jobId}-`));

  try {
    const source = join(dir, 'source');
    await pipeline(
      await this.storage.getStream(Bucket.Uploads, msg.sourceKey),
      createWriteStream(source),
    );

    const real = await sniffFormat(source);          // по сигнатуре, не по расширению
    if (real !== msg.sourceFormat) throw new PermanentError('INVALID_SOURCE');

    const converter = this.registry.resolve(msg.sourceFormat, msg.targetFormat);
    if (!converter) throw new PermanentError('UNSUPPORTED_CONVERSION');

    const out = await converter.convert(
      { path: source, options: msg.options },
      { dir, signal: AbortSignal.timeout(JOB_TIMEOUT_MS), logger: this.logger },
    );

    await this.storage.put(Bucket.Results, msg.resultKey, createReadStream(out.path));

    // Ни одного запроса в БД за всю обработку — её у воркера нет.
    await this.publisher.emit('result.completed', {
      jobId: msg.jobId, size: out.size, checksum: out.checksum,
    });

    channel.ack(raw);
  } catch (err) {
    await this.failures.handle(msg, err, channel, raw);   // permanent → result.failed, иначе → DLX
  } finally {
    await rm(dir, { recursive: true, force: true });
  }
}

5. 12 направлений из 8 кусков

// apps/data-service/src/converters/data.converter.ts
export interface DataParser {
  readonly format: DataFormat;
  parse(input: Readable, opts: ParseOptions): Promise<CanonicalDocument>;
}

export interface DataSerializer {
  readonly format: DataFormat;
  serialize(doc: CanonicalDocument, opts: SerializeOptions): Readable;
}

@Injectable()
export class DataConverter implements Converter {
  readonly id = 'data-canonical';

  constructor(
    @Inject(PARSERS) private readonly parsers: DataParser[],
    @Inject(SERIALIZERS) private readonly serializers: DataSerializer[],
  ) {}

  // Матрица — это декартово произведение минус тождественные пары.
  // 4 + 4 провайдера дают все 12 направлений.
  capabilities(): ConversionPair[] {
    return this.parsers.flatMap((p) =>
      this.serializers
        .filter((s) => s.format !== p.format)
        .map((s) => ({ from: p.format, to: s.format })),
    );
  }

  async convert(input: ConversionInput, ctx: ConversionContext) {
    const parser = this.parsers.find((p) => p.format === input.sourceFormat)!;
    const serializer = this.serializers.find((s) => s.format === input.targetFormat)!;

    const doc = await parser.parse(createReadStream(input.path), input.options);

    // Единственное место, где деревья встречаются с таблицами.
    if (serializer.format === DataFormat.Csv && !doc.isTabular) {
      if (!input.options.flatten) throw new PermanentError('NOT_TABULAR');
      doc.flatten({ separator: '.' });
    }

    const out = join(ctx.dir, 'result');
    await pipeline(serializer.serialize(doc, input.options), createWriteStream(out));
    return { path: out, size: (await stat(out)).size };
  }
}
